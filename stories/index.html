product disagreement · cross-team (pick one)

SEPA advance notices

S
Recurring buy launched on SEPA Direct Debit. Scheme rule: notify the customer before each debit, or it's refundable for 8 weeks no questions asked, disputable for 13 months. Hundreds of thousands of scheduled tasks, ~10% on SEPA DD.
T
Ship compliant advance notices before go-live, inside a scheduler service my team didn't own.
A
  • Product angle: spec wanted all six fields in the first email; four don't exist before a first payment. Verified the rulebook minimum myself and challenged the spec.
  • Cross-team angle: asked the owner for 1 hour of context plus review, not a roadmap change. "A much easier yes."
  • Shipped the compliant minimal version first, the full field set 4 weeks later.
R
Shipped inside the launch window, zero roadmap impact on the owning team. The entire recurring debit volume stopped being refundable-by-default: exposure closed before go-live.
Dual-slotted: use for product disagreement OR cross-team, never both. FREEZE the timeline: prep notes say 2 weeks, both real Revolut interviews heard 4 weeks. Verify, pick one, align everywhere. Not the "SEPA reroute email" (color detail only).

CoP/VoP name matching

S
Third-party sends had no recipient check: a mistyped name or IBAN left silently, and recovering a misdirected SEPA payment is painful, sometimes impossible.
T
Build name-IBAN verification as the proxy layer to the PSP's CoP/VoP. Spec said "near-exact match"; nobody could define it.
A
  • Gathered constraints from stakeholders: managers as constraint sources, not decision-makers.
  • Studied PSP CoP behavior. Too strict blocks nicknames and business variants; too loose lets mistakes through.
  • Proposed an explicit match policy; shipped with discrepancy-rate visibility to tune on data.
R
Roughly a quarter of checks flagged a discrepancy, each intercepted before money moved.
Decide 15% vs 25% BEFORE the interview and align everything. Never say "misdirected payments cut". Denominator: first-time, hand-typed third-party recipients.

Node secrets vs Rust proxy

S
New PII fields (IBANs) in our Kafka events; policy: nothing sensitive persisted unencrypted, and Kafka's disk retention counts. Encryption tooling existed for Rust, not our Node services.
T
A colleague proposed a permanent Rust proxy service just to encrypt our events. Decide: accept the crutch or prove a native path.
A
  • Disagreed openly but steelmanned the proxy first: new service to own, extra hop on a critical path, every future Node team inherits it.
  • Timeboxed a ~1-week spike with the proxy as the agreed fallback.
  • Added a napi encryption layer to the internal Rust lib; Vault policies via Terraform, UAT, prod behind a feature flag.
R
No proxy ever built; other Node teams adopted the library, and the colleague happily used it himself.

DocGen queue episode

S
DocGen consumed generation messages assuming delivery was effectively exactly-once. A realistic batch test sent 100 in and got ~80 out.
T
Make it 100 in, 100 out, without pretending exactly-once delivery exists.
A
  • Retries first: ~103 out, duplicates appeared.
  • Idempotency keys in a distributed cache: 100 exactly.
  • DLQ for retry-exhausted messages so nothing vanishes silently.
R
100 in, 100 out, with every layer justified by an observed failure.
Caught late in dev testing; never call it a production incident. If both Box stories come up: "same service, different episode."

production incident

Box Metadata API outage

S
PagerDuty page: the DocGen subapp failing to load. Hard dependency on the Metadata API for current file names. Writes were safe (queue-backed); users just couldn't view results.
T
Restore availability and make the freshness vs availability call live.
A
  • Fallback existed: File Search service, stale up to 15 min vs 10 s. A possibly-outdated name beats a dead product.
  • Reactivated the old integration behind the same interface and deployed.
  • Prevention: circuit breaker that trips to File Search automatically and self-recovers.
R
Zero data loss, read-only degradation; the same dependency failure now degrades instead of breaking.
Recover the outage duration before the interview; "how long were you down" is the guaranteed follow-up. Impact order that works: what was protected → what degraded and for whom → the systemic fix. Never open with the missing circuit breaker.

trade-off OR blunt feedback (one only)

TimeChimp CQRS consistency

S
The whole point of the v2 rebuild was speed and scale; there was a push to make everything strongly consistent, which would have killed both.
T
Choose what to compromise, and say so early.
A
  • Trade-off angle: CQRS with separate read/write storage; accepted eventual consistency on reads.
  • Optimistic UI updates plus websocket rollback covered the rare failed write.
  • Pushback angle: disagreed plainly and early, about the architecture not the person, with a concrete alternative in hand. "Clear and early is more respectful than letting a worse design ship."
R
Reads stayed fast, the product felt instant; the compromise was invisible to users, the failure path explicit.
Same event powers both angles. Never use both in one interview.
