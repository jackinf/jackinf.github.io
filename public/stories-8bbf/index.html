product disagreement · cross-team (pick one)

SEPA advance notices

Product angle: spec said the first email must include all six fields; four don't exist before the first payment. Challenged it, verified the rulebook minimum myself, shipped the compliant minimal version before SDD go-live, full field set 4 weeks later. Cross-team angle: didn't ask the scheduler team to reprioritize; "I needed 1 hour of their attention and their review, a much easier yes."

Shipped in 2 weeks, zero roadmap impact on the other team.

Risk framing: without the notice every recurring debit is refundable for 8 weeks no questions asked, 13 months if claimed unauthorized.

Dual-slotted: use for product disagreement OR cross-team, never both. Not the "SEPA reroute email" (that one is color detail only).

deadline pressure · ambiguity backup

Blik Deposits: happy-path first

Cut edge-case automation and breadth (shipped dark, pivot dropped plain deposits), refused to cut correctness on the money path: idempotent transitions, HMAC validation, reconciliation cron, sweeper. Safe to cut = rare + visible + manually recoverable. Nothing fails silently. Ambiguity angle: requirements changed mid-flight, re-targeted the integration in 2 weeks.

Launch-ready twice under deadline: 4 weeks + a 2-week pivot.
The ~15% lift is PROJECTED, never realized; correct it proactively. Never claim the pivot decision, that was management's call. Tester circle proves readiness, not the 15%.

ambiguous requirements

CoP/VoP name matching

Spec said "near-exact match"; nobody could define it. Too strict blocks legit payments (nicknames, business variants); too loose lets mistakes through. Gathered constraints from stakeholders (managers as constraint sources, not decision-makers), studied PSP CoP behavior, proposed an explicit policy, shipped with discrepancy-rate visibility to tune on data.

Number is a flag rate, intercepted before money moved.
Decide 15% vs 25% BEFORE the interview and align everything. Never say "misdirected payments cut". Denominator: first-time, hand-typed third-party recipients.

colleague disagreement

Node secrets vs Rust proxy

PII (IBANs) in Kafka events; policy said nothing sensitive persisted unencrypted. Colleague proposed a Rust proxy service. I disagreed openly (new service to own, extra hop, permanent crutch), steelmanned first, timeboxed a ~1-week spike with the wrapper as agreed fallback. Added a napi layer to the Rust lib, Vault via Terraform, UAT, feature flag.

No proxy ever built; other Node teams adopted it; the colleague happily used it. ↑ back to map
customer-affecting mistake

SEPA Instant near-miss (on-call)

CX flagged a return pending for days; I said "probably stuck, safe to cancel", and that quick answer was the mistake. It had actually downgraded from SEPA Instant to SDD and was still inside its settlement window. Caught it, owned it, issued a fresh retry (cancelled is terminal by design; a new payment object is correct for audit).

Customer made whole; durable CX guidance: judge by rail + settlement window, not days elapsed. ↑ back to map
data said it wasn't working · product flavor

Bank-list weighting

Splunk funnel data showed failures concentrated in specific banks sitting high in the selection list. The wrong assumption was "list order doesn't matter", not the code. Weighted the list: most-used banks up, high-error banks down.

Failed transfers cut by a few percent; the query that exposed the problem confirmed the fix. ↑ back to map
deploy gone wrong · operational data

Migration + cron flag story

Deploy went out, feature behind a flag, error spike. Triage order out loud: blast radius first (flag held, zero user impact), silenced the new cron jobs, found a partially applied migration, applied it, re-enabled, errors back to baseline.

Own the miss: API paths were flagged, the crons were not.

Prevention beat: background jobs go behind the same flag; migration completeness check in the pipeline.

Box DocGen, Java 17/21

3 years Java at Box; C# transferred smoothly. Distributed DocGen: REST endpoints, bean config per env, GCP Pub/Sub fan-out. Batch to per-file messages so files process in parallel. Follow-up ammo: inbox pattern, optimistic CAS locking, "effectively-once processing on top of at-least-once delivery" (never "exactly-once delivery"), reconciliation cron for stuck files.

owned failure · engineering slot

DocGen queue episode

Assumed reliable exactly-once delivery; a realistic batch test sent 100 in and got ~80 out. Fixed in layers: retry (~103, duplicates appeared), idempotency keys in a distributed cache (100 exactly), DLQ for retry-exhausted messages.

100 in, 100 out, with every layer justified.
Caught late in dev testing; never call it a production incident. If both Box stories come up: "same service, different episode."

production incident

Box Metadata API outage

PagerDuty page: the whole DocGen subapp failing to load, hard dependency on the Metadata API for current file names. Decision beat: File Search service as fallback, stale up to 15 min vs 10 s. Freshness vs availability: a possibly-outdated name beats a dead product. Reactivated the old integration behind the same interface, deployed. Prevention: circuit breaker trips to File Search automatically and recovers on its own.

Recover the outage duration before the interview; "how long were you down" is the guaranteed follow-up.

initiative OR manager disagreement (one only)

WDIO e2e library

The whole team paid a tooling tax: 20 tests × 4-6 min × ~3 retries, about 5 hours of flaky suite. Split the 20k-LOC file, type safety, awaits instead of sleeps, cached pre-registered test users (-2 min), local runs instead of a remote VM (-2-3 min, flakiness gone). Took a couple of months alongside feature work.

Per-test 5 min to 1 min (-80%); suite ~5 h to ~20 min; 50+ engineers adopted it.
Prep one concrete adoption action (migration guide, ported the first team's tests).
